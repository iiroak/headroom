title: OpenCode Integration
description: Route OpenCode traffic through Headroom for token compression, MCP tools, and cached model access. One command to wrap, one to unwrap.
---

Use `headroom wrap opencode` to route OpenCode LLM traffic through the Headroom proxy with a single command. The wrapper starts or reuses the proxy, writes OpenCode config, injects Headroom MCP tools, adds RTK context filtering, and launches OpenCode with the generated config.

The `headroom-opencode` npm package also exports a native OpenCode plugin. The plugin can be used directly from OpenCode config when you want in-process transport interception plus the Headroom retrieve tool.

## Quick Start

```bash
headroom wrap opencode
```

When you are done:

```bash
headroom unwrap opencode
```

## What `wrap opencode` Does

| Step | What happens |
|---|---|
| Proxy | Starts the Headroom proxy unless `--no-proxy` is set |
| Plugin install | Copies the Headroom plugin bundle into OpenCode's own plugin directory (`~/.config/opencode/plugins/entry.opencode.js`) |
| Runtime env | Sets `HEADROOM_PROXY_URL` (and `HEADROOM_OPENCODE_MODE`) so the plugin knows which proxy to route to |
| Provider routing | The plugin rewrites provider `baseURL`s at runtime and patches `fetch`/`http`; OpenCode's own provider and model selection is preserved |
| Context tool | Injects RTK (or `lean-ctx`) instructions into `~/.config/opencode/AGENTS.md` and project `AGENTS.md` |
| MCP setup | Registers the Headroom MCP server (`headroom_compress`, `headroom_retrieve`, `headroom_stats`) |
| Serena MCP | Optionally registers Serena code graph tools (`--no-serena` to skip) |
| Backup | Snapshots `opencode.json` to `opencode.json.headroom-backup` before making any changes |
| Launch | Starts the `opencode` binary through the proxy |

<Callout type="info">
  `wrap opencode` does **not** set `OPENCODE_CONFIG_CONTENT`, `OPENAI_BASE_URL`,
  or `ANTHROPIC_BASE_URL`. Routing is handled entirely by the plugin at runtime,
  which is why your existing provider and model choices survive the wrap.
</Callout>

## Server Mode (`--attach`)

By default each `headroom wrap opencode` launches a standalone OpenCode
instance. Instances do **not** share live session state: a turn's "assistant is
thinking" state lives only in the process that issued the prompt, so a second
tab in the same project shows an in-flight turn as already finished. The shared
SQLite database carries the messages but no "running" flag.

`--attach` switches to OpenCode's server mode, where one shared
`opencode serve` process owns the state and each wrap is a thin
`opencode attach` client:

```bash
headroom wrap opencode --attach
```

Run it in as many projects and tabs as you like — the first invocation starts
the shared server, the rest reuse it, and it shuts down when the last client
exits.

| | Default (standalone) | `--attach` (shared server) |
|---|---|---|
| Live streaming in a second tab of the same project | No | Yes |
| `busy` status visible to other tabs | No | Yes |
| MCP servers | One set per tab | One set per project, started lazily on the first turn |
| Isolation between projects | Full | Full (sessions and events are scoped per directory) |

The resource win comes from the MCP row: cost becomes a function of how many
projects are open, not how many tabs. Additional tabs in a project that is
already open are effectively free.

Notes:

- `--server-port` picks the shared server's port (default `4096`, OpenCode's
  own preferred port). This is separate from the proxy's `--port`.
- The server binds `127.0.0.1` only and starts without authentication. If you
  expose it beyond loopback, set `OPENCODE_SERVER_PASSWORD`.
- `--attach` cannot be combined with `--copilot-subscription`, which needs a
  private per-wrap proxy that a server shared across projects cannot provide.

## Provider Model Mapping

The generated `headroom` provider exposes these models through the proxy:

| Provider model | Upstream model |
|---|---|
| `headroom/claude-sonnet-4-6` | Claude Sonnet 4.6, 200K context, 16K output |
| `headroom/claude-opus-4-6` | Claude Opus 4.6, 200K context, 16K output |
| `headroom/claude-haiku-4-5-20251001` | Claude Haiku 4.5, 200K context, 8K output |
| `headroom/gpt-4o` | GPT-4o, 128K context, 16K output |
| `headroom/gpt-4.1` | GPT-4.1, 1M context, 32K output |

The default model is `headroom/claude-sonnet-4-6`. Change it in `opencode.json`.

## Environment Variables

| Variable | Description |
|---|---|
| `HEADROOM_PROXY_URL` | Proxy URL the plugin routes to; set by `wrap` on the launched process (or on the shared server with `--attach`) |
| `HEADROOM_OPENCODE_MODE` | `native-fetch` (default) rewrites provider base URLs; `transport` patches `fetch`/`http` instead |
| `HEADROOM_CONTEXT_TOOL` | Set to `lean-ctx` to use lean-ctx instead of RTK |
| `OPENCODE_SERVER_PASSWORD` | Basic-auth password for the shared server in `--attach` mode; unset means unauthenticated |

## Failure Learning

`headroom learn` supports OpenCode as a scan target. It reads past sessions from the newer of `~/.local/share/opencode/opencode-local.db` and `~/.local/share/opencode/opencode.db`, or from `HEADROOM_OPENCODE_DB` when you set an explicit override, and writes corrections to your project's `AGENTS.md`.

```bash
headroom learn --agent opencode --apply
```

See [Failure Learning](/docs/failure-learning) for details on the learn system.

## Persistent Installs

`headroom install` supports OpenCode as a target for persistent provider wiring. Use provider scope when you want Headroom to edit `opencode.json` directly:

```bash
headroom install apply --preset persistent-service --scope provider --providers manual --target opencode
```

This writes the Headroom provider into `~/.config/opencode/opencode.json` and keeps the proxy running on port 8787.

The default user scope only writes shell environment configuration. For OpenCode, direct provider config requires `--scope provider`.

## Native OpenCode Plugin

The `headroom-opencode` package exports `HeadroomPlugin` for direct OpenCode plugin registration. The plugin installs Headroom transport interception inside OpenCode, exposes the `headroom_retrieve` tool, and publishes Headroom metadata through the OpenCode plugin output env.

Example:

```ts
import { HeadroomPlugin } from "headroom-opencode";

export default async function plugin(input) {
  return HeadroomPlugin(input, {
    proxyUrl: process.env.HEADROOM_PROXY_URL ?? "http://127.0.0.1:8787",
  });
}
```

Use this plugin when OpenCode should intercept provider traffic in-process. Use `headroom wrap opencode` when you want the CLI to manage the proxy, config injection, MCP registration, backups, and unwrap behavior.

## Programmatic Config Helpers

The package also exports helpers for custom integrations:

```ts
import {
  buildOpencodeConfigContent,
  createHeadroomProvider,
  createHeadroomRetrieveTool,
} from "headroom-opencode";

const provider = createHeadroomProvider({ proxyPort: 8787 });
const config = buildOpencodeConfigContent({
  proxyPort: 8787,
  defaultModel: "claude-sonnet-4-6",
});
const retrieve = createHeadroomRetrieveTool({
  proxyBaseUrl: "http://127.0.0.1:8787",
});
```

## How It Works Under The Hood

1. **Plugin install**. The wrapper copies its compiled plugin bundle to `~/.config/opencode/plugins/entry.opencode.js`. This is the one loading path that always resolves: OpenCode only resolves external dependencies for files inside its own plugin tree. Exactly one file is installed, because OpenCode treats *every* `*.js` in that directory as a plugin module.
2. **Runtime routing**. `HEADROOM_PROXY_URL` tells the plugin where the proxy is. In the default `native-fetch` mode the plugin's `config` hook rewrites provider `baseURL`s to `<proxy>/v1`; in `transport` mode it patches `fetch`/`http`/`https` instead. Either way OpenCode's own provider and model selection is preserved.
3. **Session identity**. The plugin stamps `x-headroom-session-id` with OpenCode's session ID so the proxy never falls back to hashing model + system prompt — that fallback collapses concurrent tabs on the same model and project onto a single session.
4. **MCP tools**. Headroom registers `headroom_compress`, `headroom_retrieve`, and `headroom_stats` through `headroom mcp serve` unless `--no-mcp` is set.
5. **Server mode**. With `--attach`, the wrapper starts or reuses one `opencode serve` process (carrying the Headroom environment, since `attach` clients do not talk to the model themselves) and launches `opencode attach <url> --dir <cwd>`. Client markers under `~/.headroom/opencode-server-clients/<port>/` refcount the attached tabs so the server stops only when the last one exits.
6. **Unwrap**. `headroom unwrap opencode` restores `opencode.json` from the pre-wrap backup when present, strips Headroom marker blocks when no backup exists, and unregisters Headroom MCP servers.

## Troubleshooting

**OpenCode does not route through Headroom.**

Confirm the plugin is installed (`ls ~/.config/opencode/plugins/`) and that `HEADROOM_PROXY_URL` is set — the wrap command prints the env vars it sets. Then check the resolved provider: `opencode debug config` should show your provider's `baseURL` pointing at `http://127.0.0.1:<port>/v1`.

**The native plugin cannot reach Headroom.**

Set `HEADROOM_PROXY_URL` to the running proxy URL, for example `http://127.0.0.1:8787`.

**Provider not found after unwrap.**

If unwrap left the provider configured, run `headroom unwrap opencode` again, or manually restore from `~/.config/opencode/opencode.json.headroom-backup`.

**Proxy port conflict.**

Use `--port` to select a specific port, or let the proxy auto-select an available one.
